# Elevator Automation System — Siemens TIA Portal v19

Шарова архітектура програми ПЛК для елеватора. Мова — SCL.

Основний принцип: **SCADA задає мету, PLC вирішує, чи можна її виконати, і як саме.**
Жоден блок не керує механізмом напряму — будь-яка команда проходить через арбітр.

```
SCADA → Command Handlers / Route Control → Arbiter → Mechanism Layer → HAL → Physical I/O
```

## Модулі

### `Core/` — ядро

| Блок | Призначення |
|---|---|
| `FC_ArbiterMech` | Єдина точка прийняття команд. Перевіряє власника (`OwnerCur`) і стан механізму, повертає `ARB_OK` або код відмови |
| `FC_DeviceRunner` | Виконує всі механізми одним проходом: ітерує `Mechs[]`, за `DeviceType` і `TypedIndex` викликає потрібний FC |


### `Mechs/` — рівень механізмів

- `Udts/UDT_BaseMechanism` — спільний контракт будь-якого механізму: `DeviceType`, `TypedIndex`, `Status`, `Cmd`, `CmdParam1`, `FLTCode`, `Force_Code`, `OwnerCur`
- `Udts/UDT_<Type>` — специфічний стан типу (`UDT_Noria`, `UDT_Gate2P`, `UDT_Redler`, …)
- `FC_<Type>` — логіка типу; 9 реалізацій: норія, редлер, засувка 2-поз., клапан 3-поз., вентилятор, сепаратор, сушка, силоси, приймальний бункер
- `DB_Mechs` — масив `Mechs[]` і типізовані масиви

Базовий контракт + специфічний стан — це композиція, а не наслідування. Верхні шари працюють з будь-яким типом обладнання через `UDT_BaseMechanism`, не знаючи його реалізації.

### `Routes/` — маршрути

| Блок | Призначення |
|---|---|
| `FC_Route_Supervisor` | Приймає команду SCADA з mailbox, валідує, переносить у виконавчу область, виконує cleanup |
| `FC_RouteFSM` | Сам процес: `validate → acquire → execute → monitor → stop → release` |
| `UDT_RouteCmd`, `UDT_RouteStep` | Команда маршруту і крок: слот механізму, дія, параметр, очікуваний стан, timeout |
| `DB_ScadaToPlc_RouteCmd`, `DB_PlcToScada_RouteStatus` | Mailbox обміну зі SCADA за протоколом commit / ack |

Наступний крок видається лише після того, як механізм попереднього досяг заданого стану. Маршрут не має привілейованого доступу: для арбітра це такий самий власник, як SCADA.

### `Manual/` — ручне керування зі SCADA

`FC_ManualMechCmdHandler` читає запит із `DB_PlcScada_MailBox` (`Slot`, `Cmd`, `Param1`, `Commit`), передає його в арбітр від імені `OWNER_SCADA` і повертає результат разом з `AckCommit` — SCADA бачить не лише що команда надіслана, а й що PLC її розглянув.

Бізнес-логіки блок не містить: це адаптер між протоколом mailbox і моделлю ownership.

### `HAL/` — абстракція обладнання

`FC_HAL_Read` переносить фізичні входи в логічні поля UDT (`DI_Speed_OK`, `DI_Breaker_OK`, `DI_Opened_OK`, …), `FC_HAL_Write` — логічні виходи на канали (`DO_Run`, `DO_Open`, `DO_Close`). Логіка механізму не знає адрес модулів, тому зміна адресації локалізується в HAL.

Обидва блоки генеруються з конфігурації проєкту.

### `Tags/` — таблиці тегів TIA Portal

- `Constant.csv` — довідники проєкту: `STS_*` (стани), `CMD_*` (команди), `FLT_*` (аварії), `ARB_*` (коди відмов арбітра), `OWNER_*`, `TYPE_*`, `ROUTE_*`
- `Mechs.csv` — кількості механізмів (`MECHS_COUNT`, `NORIAS_COUNT`, …)
- `Common.csv` — глобальні теги

## Про цей репозиторій

Витяг коду для ілюстрації архітектури. Генератор конфігурації, симулятори механізмів і тестові блоки сюди не входять — тому `Main.scl` містить виклики, яких у цьому репозиторії немає.
